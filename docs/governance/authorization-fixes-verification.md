# التحقق من إصلاحات الصلاحيات الثلاثة

تاريخ التنفيذ: 2026-10-02.

الحالة: إصلاحات محلية واختبارات معزولة مكتملة، **غير منشورة وغير متحقق منها على خدمة Render الحية**. لا تغيير لصفوف المستخدمين أو الصلاحيات، ولا ترحيل أو إعادة تشغيل للخادم.

## نطاق الإذن

طلب المستخدم تنفيذ الإصلاحات الثلاثة بعد اختبارات إعادة الإنتاج. لم يُطلب تنفيذ كامل سياسة الحوكمة، أو تقييد admin، أو تفعيل آلية الطوارئ المؤجلة.

## الإصلاحات

### 1. مطابقة صاحب إسناد الدور

- PATCH/DELETE يربطان معرف الإسناد بمعرف المستخدم في الرابط.
- شرط المالك داخل UPDATE/DELETE نفسه مع RETURNING، وليس قراءة مسبقة منفصلة يمكن أن يتغير بعدها المالك.
- رفض حقول الهوية والمالك والحقول غير المعروفة في PATCH، والتحقق من المعرفات وأنواع الحقول.
- السجل المفقود أو المختلف المالك يعيد 404 بلا تعديل؛ جسم غير مقبول يعيد 400.
- لا إبطال لذاكرة الصلاحيات إلا لصاحب السجل الذي تغيّر فعلًا.
- عمليات admin المشروعة تبقى متاحة؛ مطابقة هوية المورد ليست سياسة تقليص لصلاحياته.

### 2. سقف المنح وإغلاق المداخل البديلة

- امتلاك users:edit أو rbac_management وحده ليس تفويضًا بإدارة السلطة العامة.
- مسارات المنح العامة والأدوار وإسنادها والاستثناءات والفروع والقوالب محصورة بـ admin.
- مسار تفويض التشغيل المعتمد بقي دون تغيير، بما فيه سقف المسؤول واختيار الموظف والفرع وحماية الحسابات.
- منع تجاوز هذه الحدود بتعديل role/jobTitle/branchId/branchIds/password/isActive عبر تعديل المستخدم العام لغير admin، ومنع تعديل حساب admin من هذا المسار.
- إنشاء الحساب العام لغير admin لا يسمح بدور إداري أو مسمى/منح فروع؛ التعديل العادي للأسماء والملف بقي متاحًا للحسابات المسموحة في المسار الحالي.

**أثر التوافق المقصود:** غير admin الذي كان يعتمد على users:edit وحدها لإدارة السلطة العامة سيحصل على 403. لا يوجد تحويل تلقائي له إلى مفوّض ولا حذف لمنحه المخزنة. المفوضون المعتمدون يستخدمون مسار التفويض المحدود القائم؛ لم ننشئ نظام تفويض تنظيميًا موازياً.

### 3. فحص نوع العملية قبل منح الدور التلقائي

- يُستنتج الإجراء من HTTP قبل منح الأدوار الخاصة، ولا يكفي وجود الوحدة في خريطة الدور.
- hr_specialist وfinancial_manager وoperations_manager تحتاج الإجراء المستنتج/الصريح ضمن المسموح.
- الحفاظ على قيود الأدوار الصلبة، والمنع الصريح القائم للتشغيل، وحدود الفروع، ومنح المستخدم الإضافية المشروعة.
- الحفاظ على اتساع صلاحيات hr_manager الموجود أصلًا ضمن إجراءات النظام المعروفة؛ لم يُخترع له قالب أضيق.
- admin يحتفظ بتجاوزه القائم؛ لم تُفعّل عليه سياسة المنع الجديدة.

## التحقق النهائي المجمع

الأمر التالي نجح: **7 ملفات، 981 اختبارًا، دون فشل**.

```sh
./node_modules/.bin/vitest run --config vitest.config.ts \
  tests/governance-global-writers.test.ts \
  tests/governance-route-isolated.test.ts \
  tests/governance-action-isolated.test.ts \
  tests/governance-assignment-storage.test.ts \
  tests/employee-account-delegation-policy.test.ts \
  tests/employee-account-delegation-cashier.test.ts \
  tests/employee-delegated-operations.test.ts
```

- اختبارات إعادة الإنتاج السابقة أصبحت تتحقق من الرفض وبقاء البيانات الوهمية دون تغيير، مع بقاء حالات السماح المشروع.
- اختبارات التخزين تنفذ الطرق الفعلية المستخرجة من الشيفرة مع بديل قاعدة بيانات في الذاكرة، وتشمل تغير المالك بين الخطوات؛ ليست برهان تزامن PostgreSQL حقيقيًا.
- الاختبارات لا تتصل بقاعدة البيانات أو تسجيل الدخول؛ الهوية والمدخلات اصطناعية.
- نجح تجميع الخادم بواسطة esbuild إلى ملف مؤقت دون تشغيله. ظهرت تحذيرات لتكرار طرق قائمة في storage ومفتاح PDF خارج التغييرات؛ التجميع ليس فحص TypeScript كاملًا.
- فحص git diff --check ناجح.
- لقطة المعاينة أظهرت صفحة تسجيل الدخول دون خطأ ظاهر. لم يُعد تشغيل الخادم، لذلك ليست دليلًا على تحميل الإصلاحات أو اختبارها عبر المتصفح.

## حدود التحقق وملاحظات خارج الدفعة

**تحديث التحقق النهائي:** أُعيد إنتاج الفشلين أدناه على نسخة ما قبل الإصلاحات، ثم حُدث الاختباران ليتوافقا مع التحقق الفعلي مع الحفاظ على حالات الرفض. نجحا 9/9، كما نجح بناء الإنتاج الكامل. التفاصيل وخطوات النشر والرجوع في [قائمة نشر Render الآمن](render-safe-release-checklist.md). الوصف التالي سجل للملاحظة الأصلية، وليس عائقًا ما زال دون حسم.

فحص أوسع أثناء العمل سجل فشلين إضافيين في `production-development-manager.test.ts` و`upload-file-middleware.test.ts`: الأول توقع نص قديم في مسار توجيه المطبخ، والثاني توقع وصول فرع مع بديل منح حديث يعيد قائمة فارغة. لم نعدل هذين الاختبارين أو مصادرهما، ولم ننفذ مقارنة كاملة مع النسخة السابقة لحسم علاقتهما بهذه الدفعة؛ **لا ندعي نجاح مجموعة الاختبارات الكاملة للمشروع**.

لم يُختبر تسجيل الدخول والجلسات وواجهات إدارة المستخدمين على خادم محمل بالتغييرات، ولا متانة المعاملات والتدقيق على قاعدة فعلية. لم تُنفذ اختبارات اختراق للإنتاج، ولم يُحسم معرّف النسخة المنشورة.

سبب عدم إعادة التشغيل: مسار بدء الخادم يتضمن إجراءات قاعدة بيانات تلقائية في server/db.ts وإعداد تخزين في server/index.ts. تشغيله دون التحقق من هدف الاتصال قد يتجاوز حدود عدم تغيير البيانات الحية. لذلك اقتصر التحقق على الاختبارات المعزولة وتجميع الشيفرة.

## قبل النشر

تثبيت نسخة Render وهدف الاتصال، مراجعة أثر حصر إدارة الصلاحيات العامة على الحسابات غير admin، وتجربة نسخة مرشحة على قاعدة اختبار معزولة مع خطة رجوع. النشر يحتاج موافقة منفصلة، ولا يُستبدل بنشر مشروع Replit المختلف.
