# نتائج اختبارات الصلاحيات المعزولة

تاريخ التنفيذ: 2026-10-02.

**هذه وثيقة نتائج ما قبل الإصلاح.** نفّذ المستخدم لاحقًا تفويضًا منفصلًا للإصلاحات الثلاثة، ووُثقت نتائجها في [التحقق من الإصلاحات](authorization-fixes-verification.md). حالات KNOWN GAP المشار إليها أدناه حُولت إلى اختبارات منع؛ تبقى الأرقام والنتائج هنا سجلًا للفحص السابق، لا وصفًا للشيفرة الحالية.

## التفويض وحدود التنفيذ

وافق المستخدم على **الاختبارات المعزولة فقط** لثلاث مجموعات من المشكلات، دون إصلاح أو تغيير الموقع الحي. أضيفت ملفات الاختبار وهذه الوثيقة فقط؛ لم يتغير تطبيق الإنتاج أو حساب أو صلاحية أو جلسة، ولم تُشغّل ترحيلات أو خدمات أو اتصالات بقاعدة البيانات.

هذه متابعة لوثيقة [جرد المرحلة الأولى والسياسة](phase1-inventory-and-policy.md). ليست إعلان إغلاق جميع متطلبات المرحلة الأولى أو تفويضًا لتنفيذ السياسة الجديدة.

## النتيجة المختصرة

**54 حالة اختبار** توثق السلوك الحالي: 21 حالة موسومة KNOWN GAP تعيد إنتاج ثغرات، و33 حالة مقارنة/ضبط. نجاحها يعني أن النتائج تطابق الملاحظة، **ولا يعني أن النظام آمن أو أن الثغرات أُصلحت**. لم نختبر الاستغلال على الموقع الحي ولم نثبت تطابق نسخته مع الشيفرة المفحوصة.

| المجموعة | النتيجة المثبتة في الاختبار | حدود الاستنتاج |
|---|---|---|
| ملكية إسناد الدور — G02 | مستخدم غير admin لديه users:edit يستطيع تقديم مستخدم آخر في الرابط مع إسناد يملكه هو أو طرف ثالث؛ PATCH يعيد 200 ويعدّل الإسناد وDELETE يعيد 204 ويحذفه في الذاكرة. كما يُمرّر userId من جسم PATCH ويُعاد إسناد السجل | التسجيل والوسيط والمعالج من الشيفرة الحالية؛ التخزين بديل ذاكرة مطابق للعقد المفحوص، لا تنفيذ SQL |
| سقف منح الصلاحيات — G01 | مستخدم employee افتراضي يملك users:edit فقط يستطيع إرسال users:create/edit/delete وsettings:edit/delete وsalary_closing:approve/export لحساب آخر؛ النتيجة 200 وتمرير المنح إلى التخزين والتدقيق الافتراضيين | لا إثبات لوجود هذا المستخدم في الإنتاج أو وصوله الفعلي. تغيير صفوف منح لحساب admin افتراضي لا يعني إثبات تغيير سلطته الفعلية أو تعديل حساب admin حقيقي |
| نوع الإجراء — G03 | عند حذف وثيقة في الفرع المسموح، يمر hr_specialist الذي لا يتضمن دوره delete من requirePermission بلا إجراء صريح؛ ينفذ معالج DELETE الحقيقي ويزيل الوثيقة الوهمية. كذلك تمر كتابات employee_reports عبر وسيط HR specialist/financial manager عند إغفال الإجراء، وتُرفض عند تحديد الإجراء المحظور صراحة | حذف الوثيقة مثال لمسار فعلي؛ مصفوفة employee_reports تثبت سلوك الوسيط فقط، لا وجود كل طرق الكتابة في مسارات التقارير |

## تفاصيل الحالات المقابلة

### إسنادات الأدوار ومنح الصلاحيات — 34 حالة

الملف: `tests/governance-route-isolated.test.ts`.

- غياب users:edit، أو امتلاك users:view فقط: رفض 403 دون تعديل الذاكرة.
- استخدام معرف المستخدم نفسه في الرابط: الرفض القائم يعمل لغير admin.
- استبدال معرف المستخدم في الرابط مع إبقاء معرف الإسناد: يكشف غياب مطابقة المالك.
- تمرير userId داخل جسم PATCH: يكشف قبول تغيير صاحب الإسناد دون تحقق مناسب.
- إسناد مفقود: PATCH يعيد 404؛ DELETE يعيد 204 وفق السلوك الحالي.
- viewer يُمنع من الكتابة حتى مع منح افتراضي زائد.
- تعديل admin لنفسه يظل مسموحًا في الضوابط المقابلة؛ لا تعديل لسياسة admin.
- فحص مفردات الوحدات والإجراءات يستبعد القيم غير المعروفة، لكنه لا يضع سقفًا لما يجوز للمانح منحه.
- تم تمرير أهداف وهمية من أدوار employee وadmin وbusiness_owner وshareholder، ومن فرع آخر. معالج المنح لا يقرأ أدوار الأهداف أو فروعها في الحالات المختبرة؛ نجاح الطلب لا يثبت صلاحية إدارية مشروعة لإدارة هذه الأهداف.
- جرى فحص معاملات الاستثناءات الموروثة والتدقيق التي تُرسل للتخزين، لا ضمانات حفظها على قاعدة بيانات حقيقية.

### نوع الإجراء وحذف الوثائق — 20 حالة

الملف: `tests/governance-action-isolated.test.ts`.

- مستخدم employee بصلاحية عرض فقط: GET يمر وPOST/PUT/PATCH/DELETE تُرفض.
- hr_specialist وfinancial_manager: 8 حالات تقارن الإجراء المستنتج/المغفل بالإجراء الصريح؛ العمليات غير الموجودة في الخريطة تمر عند الإغفال.
- وثيقة وهمية داخل الفرع: أخصائي الموارد البشرية يحذفها رغم غياب delete.
- الوثيقة نفسها في فرع آخر: رفض 403 والوثيقة باقية، باستخدام مساعدات النطاق الفعلية.
- مستخدم عادي بصلاحية عرض فقط: رفض الحذف.
- مستخدم عادي مع delete صريحة: حذف مشروع داخل الفرع.
- admin: السلوك القائم يظل مسموحًا؛ لا قيود جديدة.
- غياب الهوية المصادق عليها عند وسيط الصلاحيات: 401.

## كيف ضُمِن العزل؟

- لا تشغيل لـ server/index.ts ولا استيراد للتسجيل الكامل لمسارات التطبيق.
- اختبار الإسناد والمنح يقرأ AST ويشغّل التسجيلات الأصلية والوسيط requirePermission وتوابعه وgetCurrentUser الفعلي داخل VM محدود. لا process أو اتصال أو timers أو SQL؛ الاعتماد غير المتوقع يفشل صراحة.
- اختبار الإجراء يستورد وسيط auth الفعلي مع استبدال storage/db/security ومدخلات OTP قبل التحميل، ويمنع اتصالات Socket وfetch أثناء الحالات. لا تُقرأ أسرار أو ملفات بيئة.
- معالج حذف الوثيقة ومساعدا getBranchScope وresolveHrBranchScope مأخوذة من AST، مع مساعدات نطاق auth الفعلية. عمليات قاعدة البيانات بديل ذاكرة يتحقق من الجدول ومعرف الوثيقة المتوقعين.
- لا نسخ لمنطق التفويض في بدائل الاختبار. بدائل التخزين تحاكي بيانات القراءة والكتابة فقط.
- مصادقة الجلسة نفسها **ليست ضمن الاختبار**: تبدأ الحالات بطلبات ذات currentUser وauthPermissions وهميين، بدل تسجيل الدخول أو الاتصال بـ Clerk.
- حالات admin حسابات وهمية؛ لم نقرأ أو نعدّل الحساب الحقيقي.

## إعادة التشغيل

من جذر المشروع، باستخدام Vitest المثبت محليًا:

```sh
./node_modules/.bin/vitest run --config vitest.config.ts \
  tests/governance-action-isolated.test.ts \
  tests/governance-route-isolated.test.ts
```

شُغلت كل حزمة على حدة أثناء التنفيذ: 20/20 و34/34. الأمر المجمع أعلاه لإعادة التشغيل، وليس ادعاء تشغيل اختبار أوسع أو اختبار المتصفح.

**تنبيه للمطور:** الاختبارات الموسومة KNOWN GAP اختبارات توصيف للخلل القائم. عند إصلاح الخلل يجب تحويلها إلى توقع الرفض الأمني والتحقق من عدم تغير البيانات، لا حذف الحماية لتظل هذه التوقعات ناجحة. أبقِ الحالات المقابلة المسموحة والمرفوضة.

## ما لم يُثبت وما لم يُنفّذ

- لا إصلاح للشيفرة، ولا ترحيل أو نشر أو إعادة تشغيل.
- لا اختبار تسجيل الدخول أو الجلسات أو التخزين الحقيقي أو المعاملات أو متانة سجل التدقيق.
- لا إثبات لتعرض بيانات فعلية أو لاستغلال سابق أو لوجود مستخدم حي قادر على تنفيذ السيناريو.
- لا اختبار شامل لجميع الأدوار أو المسارات أو القرارات الجديدة؛ فحص الزمن والنطاق المتعدد والمنع/الوراثة خارج هذه الدفعة.
- لا إثبات لتطابق معرّف نسخة Render المنشورة مع شيفرة مساحة العمل.

## الخطوة التالية المقترحة — تحتاج إذنًا منفصلًا

إصلاح ملكية الإسنادات وحقول PATCH أولًا، ثم سقف المنح وحماية الأهداف، ثم استنتاج الإجراء للأدوار الخاصة. يجب الحفاظ على صلاحيات admin الحالية، والتفويض الفردي المعتمد للتشغيل، والوصول المشروع داخل الفروع، وتحويل حالات إعادة الإنتاج إلى اختبارات رفض قبل أي نشر.
