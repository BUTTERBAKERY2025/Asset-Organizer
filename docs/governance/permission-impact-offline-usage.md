# Offline phase-2 permission comparison

This read-only tool supports the affected-account/context review required by
[phase 2](phase2-contextual-permissions.md). It does **not** complete that review,
adapt routes, apply manual migration 050, or authorize production activation.

## Run

```sh
npx tsx scripts/compare-permission-impact.ts /approved/local/sanitized.json
# Or provide the same JSON on stdin:
cat /approved/local/sanitized.json | npx tsx scripts/compare-permission-impact.ts -
# Focused offline tests (no app or database):
npx vitest run --config vitest.config.ts tests/permission-impact-offline.test.ts
```

The CLI reads only the explicitly supplied JSON file/stdin, and prints a JSON
report to stdout. It never loads the application, storage, database, dotenv,
environment configuration, or a network client; it has no runtime write API.
Invalid input or unavailable files fail explicitly with a nonzero exit code and
no report. Shell redirection, if used by the operator, is outside the tool.

## Input contract (schemaVersion 1)

All objects reject extra properties: strip names, email, tokens, and unrelated
account data before supplying the file. Identifiers can be stable pseudonyms.
No export/query utility is included: obtain an approved, sanitized snapshot
through a separately reviewed process.

Required top-level fields:

- `schemaVersion`: `1`.
- `evaluatedAt`: explicit ISO timestamp with timezone (`Z` or offset). There is
  no wall-clock default; all decisions use this same instant.
- `baselineId`: identifier for the independently supplied old-decision evidence.
- `accounts`: array of records described below.
- `checks`: array of records described below.

Each account requires `userId`, `role`, `sourceMode`, `direct`, `roles`, and
`overrides`. `role` is the actual auth role identifier; exactly `admin` retains
the unconditional bypass. Do not infer it from permissions or job titles.

- `sourceMode`: `null`, `"direct"`, or `"inherit"`; absence is an error, not a
  fallback. `null` means a confirmed absent source record in the supplied
  snapshot, **not** an unavailable source table.
- `direct`: `{ "module": string, "actions": string[] }[]`, including empty-action
  rows when present.
- `roles`: expanded assignment/permission tuples, each with `module`, `action`,
  positive integer `permissionId`, `scopeType`, nullable `branchId`, nullable
  positive integer `departmentId`, nullable string `startDate`, nullable string
  `endDate`, and boolean `isActive`.
- `overrides`: each with `module`, `action`, positive integer `permissionId`,
  boolean `allow`, nullable `branchId`, nullable positive integer `departmentId`,
  and nullable string `expiresAt`.

Every check requires a unique `id`, an existing `userId`, `module`, `action`,
`context`, and boolean `oldAllowed`. `context` is an object with optional
nullable `branchId` and `departmentId`. `{}` explicitly evaluates a resource
whose context is unknown. Supply actual route/resource contexts, not a claimed
client branch, and enumerate each relevant action separately. Unique account
and check identifiers are enforced. Accounts without checks are explicitly
reported as unchecked.

**Old decisions are supplied evidence**, not generated by this tool: obtain
`oldAllowed` from the approved old revision/decision evidence for the *same*
account, module, action, resource context and evaluation time. This avoids
inventing an undocumented historical flattening policy. The tool validates
the shape, but cannot verify provenance, currency, completeness, or agreement
of that evidence with the tuples. Do not mix old HTTP outcomes and new
tuple-layer decisions without separately reconciling other authorization
policies.

## Interpretation and limits

The new side calls the real pure `permission-decision.ts` normalizer/checker.
It preserves current source selection, tuple action/scope pairing, directional
aliases, deny precedence, and inclusive start/exclusive end/expiry boundaries.
Explicit direct-empty remains empty; inherited tuples are never unioned into
it. Independent overrides still apply. Malformed row timestamps retain the
resolver's fail-closed grant / conservative deny behavior.

Reports contain aggregate counts, changed/unchecked account identifiers, and
one row per supplied check. Rows are sorted by check identifier. A fixed input
and evaluation instant produce the same result. Reasons include
`unknown-context`, `expired`, `source-empty`, `explicit-deny`, `scope-mismatch`,
`inactive`, `not-started`, `invalid-time`, and `invalid-scope`. Reasons are
diagnostics, not all fatal: an expired candidate can coexist with a live grant,
and an empty base can coexist with an override grant. `source-empty` describes
the selected base as a whole, not merely a missing requested action.

The comparison layer is **pure permission tuples plus admin bypass**, not
full HTTP authorization. It deliberately does not reproduce auth's intrinsic
non-admin role auto-grants, route-specific policies, ownership, collection
filtering, sessions, or resource lookup. Those need separate route/account
review and success/denial tests. Unknown context never supplies missing scope.
The tool does not prove a handler filters returned data correctly.

Generated test fixtures prove only deterministic mechanics and resolver parity.
They are **not actual-account impact evidence**. A report over approved current
data establishes only the supplied checks at the supplied instant; unchecked
accounts, unenumerated routes/actions/resources, and missing intrinsic policies
remain outside its coverage. Keep the phase-2 activation gates in place until
the account/context review, affected-route adoption, manual 050, and deployment
approval are independently complete.
