# المرحلة الأولى: جرد الوضع الفعلي وتحديد السياسة

تاريخ الفحص: 2026-10-02. الحالة: الجرد الموثق منجز ضمن الحدود أدناه؛ أكد المستخدم اتصال الخدمة الحية بالقاعدة المفحوصة بعد مراجعة إعدادات Render. اعتماد السياسة وتطابق النسخة المنشورة مع الشيفرة المفحوصة معلقان. ليست شهادة خلو من الثغرات ولا إذنًا للترحيل.

## 1. حدود السلامة والأدلة

- المستخدم أكد أن النظام يعمل وعليه مستخدمون. لم نعدل أي ملف تطبيق أو صلاحية أو حساب، ولم نشغل ترحيلًا أو اختبارات كتابة أو إعادة تشغيل أو نشر.
- جرى فحص الشيفرة والجداول التنظيمية والأمنية المختارة. لا ندعي مراجعة كل مسار أو كل سياسة RLS.
- الاستعلامات الخارجية عبر Supabase MCP على الهدف الموثق سابقًا في docs/live-runtime-identity.md، داخل BEGIN READ ONLY مع statement_timeout قدره 4 ثوانٍ. النتائج إحصائية وبيانات بنية فقط، بلا أسماء موظفين أو بيانات دخول أو رواتب.
- تعريف البيئة: مصدر الشيفرة هو مساحة العمل. قاعدة البيانات هي الهدف الخارجي الذي سبق اعتماده، وليست قاعدة Replit المحلية. لا يثبت اتصال MCP وحده أن حركة Render الحية تستخدم هذا الهدف أو هذه الشيفرة.
- تحديث 2026-10-02: أكد المستخدم أنه تحقق من إعدادات Render وأن مشروع Supabase مطابق للهدف المفحوص. مصدر إثبات الربط هو تأكيد مالك الخدمة، وليس تحققًا مستقلًا من المزود. لم يقدم معرّف النسخة المنشورة؛ لا ننسب نتائج مراجعة الشيفرة تلقائيًا إلى النسخة الحية.
- الجرد لقطة زمنية؛ لم نقفل الجداول ولا نوقف المستخدمين. الاستعلامات المتعددة ليست لقطة ذرية واحدة، وقد تتغير الأعداد بعد القراءة.
- الفحص ليس إصلاحًا. اختبارات الاستغلال وإثبات المنع لم تُشغّل على الموقع الحي.

### دلالة الأرقام

- وجود 196 منعًا يستلزم الحفاظ على مضمونها وتحديد أثرها الفعلي قبل أي تحويل. العدد لا يثبت أن كل المسارات تطبقها.
- الجمع بين الإسنادات والمباشر في 11 حسابًا يجعل تغيير قاعدة الوراثة خطر توافق ملموسًا؛ ممنوع دمج المصدرين تلقائيًا.
- 8 إسنادات مرتبطة بفرع تتطلب مقارنة دقيقة عند إصلاح النطاق. وجودها لا يثبت تعرض بيانات؛ يلزم حساب القرار لكل مورد.
- عدم وجود تفويضات زمنية منتهية/مستقبلية الآن لا يلغي الخلل البرمجي المتعلق بالتواريخ.
- عدم ظهور جدول sectors ضمن الأسماء المفحوصة، وعدم وجود قطاع/أب في departments، لا ينفي وجود تنظيم آخر خارج مجموعة الفحص.

| سجل مخاطر مرتبط بالأدلة واختبارات قبول لاحقة | منجز؛ إثبات التشغيل/الإصلاح لم ينفذ |
| سجل قرارات يفرق المقترح عن المعتمد | منجز؛ الاعتماد التجاري معلق |
| تحديد قاعدة البيانات المستخدمة بواسطة Render | مؤكد بإفادة المستخدم بعد التحقق من إعدادات الخدمة؛ ليس تحققًا مستقلًا من المزود |
| تطابق الشيفرة المفحوصة مع النسخة المنشورة | معلق؛ لم يقدم معرّف النسخة المنشورة |
| مقارنة صلاحيات كل حساب متأثر وتصنيف الفروقات | مؤجلة حتى اعتماد القواعد؛ لا تُستبدل بالأعداد الإجمالية |
| التأكد من عدم إجراء تغييرات تشغيلية | لم نصدر أي كتابة بيانات أو تعديل تطبيق أو إعادة تشغيل أو نشر |

الحكم: حُدد هدف قاعدة البيانات الحية بإفادة المستخدم. لا تُغلق بوابة المرحلة الأولى كاعتماد كامل قبل حسم تطابق النسخة المنشورة واعتماد القرارات الحساسة وأصحابها. يمكن إعداد اختبارات محلية معزولة لإثبات الثغرات المؤكدة بعد إذن المرحلة التالية، دون انتظار أو تغيير بيانات الإنتاج.

## 10. ترتيب المعالجة المقترح بعد الاعتماد

1. G02 ملكية الإسناد وحقول الطلب؛ G01 سقف المنح وحماية الهدف.
2. G03 التحقق من الإجراء بمقارنة الأدوار الحالية، دون إلغاء وصول مشروع.
3. G04/G05 توحيد النطاق/المدة/المصادر مع الحفاظ على قرارات المنع.
4. ذرية التغييرات، فصل إجراءات العمل الحساسة، دورة الموظف، التدقيق.
5. التنظيم والقوالب بعد استقرار القاعدة المشتركة، مع إصدار وتجربة متعددة الإدارات.

لا تعتبر هذه الوثيقة تفويضًا لتغيير صلاحيات الإنتاج أو نشر إصلاحات تلقائيًا.
