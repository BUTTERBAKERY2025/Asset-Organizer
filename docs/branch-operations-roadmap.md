# خارطة تنفيذ عمليات الفروع

## الهدف والحدود

هذه خارطة تنفيذ قابلة للتقسيم والنشر التدريجي للوحة تشغيل الفرع. المرحلة الأولى أدناه منفذة في التطبيق، أما المراحل اللاحقة فهي خطة وليست وصفاً لميزات منجزة. المراجعة أدناه **مراجعة ساكنة للمصدر الحالي**؛ لم تُفحص بيانات الإنتاج ولم تُنفّذ كتابة عليها، وعبارة «غير متحقق» لا تعني أن الوظيفة غير موجودة خارج المصادر التي تمت مراجعتها.

المبدأ: تكون `branch_id` هو نطاق كل سجل تشغيلي، مع إعادة استخدام `branches` و`branch_employees` و`users` والمنتجات والمرفقات الحالية. لا تُنشأ نسخ موازية للفروع أو الموظفين أو الملفات.

## جرد ما هو موجود فعلاً

| الاحتياج | التصنيف | الدليل والحد المتبقي |
|---|---|---|
| الصيانة | **موجود جزئياً** | `maintenance.tsx` يعرض أصناف `inventory_items` بحالات صيانة/تالف/مفقود ويطبع ويصدّر؛ ما زالت دورة بلاغ صيانة وإسناد وموعد وإغلاق وتكلفة وصور غير منفذة. |
| المنتجات غير المتوفرة | **موجود جزئياً** | `branch_products.is_active` يضبط إتاحة منتج نقطة البيع، وطلبات المطبخ تدعم حالة بند `unavailable`؛ لا توجد دورة تشغيلية موحدة لسبب عدم التوفر ومدته وإعادة الإتاحة. |
| الهالك | **موجود ومتحقق بالمصدر** | `waste_reports` و`waste_items` وحالات اعتماد وصورة وواجهات `/api/waste-reports` وصفحة `display-bar-waste.tsx`. |
| مراجعات Google | **غير متحقق** | لم يظهر نموذج/مسار مخصص أو مزامنة Google Business Profile. لا يُفترض عدم وجود خدمة خارجية غير ممثلة بالمستودع. |
| الشهادات الصحية والإقامات | **موجود ومتحقق بالمصدر** | طبقة قراءة موحدة تجمع بيانات `employee_documents` مع حقول ملف الموظف القديمة عند غياب وثيقة فعلية من النوع نفسه (حتى المؤرشفة تمنع البديل)، وتستخدم الفرع الحالي للموظف وتاريخ السعودية وحدّ 30 يوماً شاملاً. تعرض إدارة HR والتقارير وبطاقة الفرع الإسقاط الوصفي نفسه، بينما يبقى بديل ملف الموظف للقراءة فقط ولا ترسل واجهة التقارير روابط ملفات أو مرفقات. |
| الأهداف والمبيعات الشهرية | **موجود ومتحقق بالمصدر** | `branch_monthly_targets` وتخصيصاتها، مسارات الأهداف، لوحات التخطيط والمتابعة، ومصادر المبيعات اليومية/تقارير التشغيل. يلزم ضبط إظهار المبيعات في اللوحة الجديدة بصلاحية مستقلة. |
| تدريب الموظفين | **غير متحقق كنطاق فروع** | توجد بيانات تدريب للمتقدمين ولأعضاء المجلس، لكن لا يثبت منها برنامج تدريب موظف فرع مع حضور ونتيجة واعتماد. |
| العهدة النقدية | **موجود جزئياً** | يوميات الكاشير والإغلاق والفروقات والتوقيعات موجودة، ويوجد عرض «العهدة» بالنموذج؛ لا يثبت دفتر عهدة مستقل بتسليم/استلام ومسؤول حالي وربط محاسبي. |
| السكن والغرف والتنظيف | **غير متحقق كنطاق تشغيلي** | بدل السكن ومخطط مناطق الفرع ووظيفة عامل نظافة موجودة، لكنها ليست إدارة مساكن وغرف وإشغال وفحوص تنظيف. |
| جداول الفرع/الغرف | **موجود جزئياً** | جداول الموظفين والشفتات وقوائم فتح/إغلاق الفرع موجودة؛ لم يتحقق جدول غرف سكن أو تنظيف دوري مستقل. |
| الصلاحيات/انتهاء المنتجات | **موجود جزئياً** | انتهاء وثائق الموظفين متحقق. «منتهي الصلاحية» سبب هالك، لكن لا يثبت سجل دفعات منتجات بتاريخ صلاحية وتنبيه قبل الانتهاء. |
| الزيارات | **موجود جزئياً** | `visitors` و`visitor_logs` يدعمان سجل الزيارات؛ يلزم قرار هل المقصود زيارات ضيوف، زيارات إشراف للفرع، أم كلاهما قبل دمجهما. |
| الشكاوى | **موجود ومتحقق بالمصدر** | `branch_complaints` ومسارات `/api/branch-complaints` وصفحتها تنفذ نطاق الفرع والتصنيف والأولوية والمالك وموعد الاستجابة والمرفقات وسجل الأحداث وانتقالات البدء والحل والإغلاق وإعادة الفتح مع قفل نسخة؛ وتعرض اللوحة عدادي المفتوح والمتأخر وروابطهما. |
| المشتريات | **موجود ومتحقق بالمصدر** | `purchasing_requests` وبنودها ودورة pending→approved/rejected→ordered→received/cancelled، مع صفحة ومسارات API. |
| تقرير الموظف الشهري/الصيانة | **موجود جزئياً** | تقارير موظفين شهرية واسعة وتقارير صيانة أصناف منفصلة موجودة؛ لا يوجد تقرير موحد يربط مسؤوليات موظف الشهر ببلاغات الصيانة دون قرار أعمال. |
| طلبات المطبخ | **موجود ومتحقق بالمصدر** | دورة طلب الفرع، الاعتماد، التجهيز، الإرسال، الاستلام والفروقات موجودة، مع نطاق فرع وإشعارات. |
| المصروفات النثرية | **موجود جزئياً** | `payment_requests` يدعم مصروف/سلفة، لكن لا يثبت صندوق نثريات برصيد افتتاحي، تغذية، سندات، تسوية وإقفال مرتبط فعلياً بالمالية. |
| تطبيقات التوصيل | **موجود جزئياً** | إدخال يدوي حسب التطبيق في يومية الكاشير وتقارير تجميع موجودان؛ لا توجد مزامنة خارجية موثقة مع مزودي التطبيقات. |

## معمارية الإكمال المقترحة

### نموذج البيانات المفاهيمي

تُضاف الجداول فقط عند وصول مرحلتها، تحت تسمية ثابتة مثل `branch_ops_*`:

- `branch_ops_cases`: سجل موحد للبلاغات التشغيلية التي تشترك فعلاً في دورة واحدة (صيانة/شكوى/زيارة إشراف)، ويتضمن `branch_id`, `type`, `status`, `priority`, `owner_user_id`, `reported_by`, `due_at`, `resolved_at`. لا تُجبر المجالات المختلفة على هذا الجدول إذا اختلفت قواعدها.
- `branch_ops_case_events`: انتقالات غير قابلة للمحو تسجل الحالة السابقة والجديدة والفاعل والوقت والسبب.
- `branch_ops_product_unavailability`: المنتج/الفرع، السبب، البداية والنهاية المتوقعة والفعلية، ومن أعاد الإتاحة؛ قيد يمنع فترتين مفتوحتين للمنتج نفسه في الفرع نفسه.
- `branch_ops_expiry_lots`: مرجع صنف/منتج موجود، رقم دفعة اختياري، الكمية والوحدة وتاريخ الصلاحية والحالة؛ لا يعدّل المخزون من تلقاء نفسه.
- `branch_ops_checklist_templates`, `branch_ops_checklist_runs`, `branch_ops_checklist_results`: فقط للقوائم غير المغطاة بقوائم فتح/إغلاق الشفت الحالية، مع نسخة مجمدة للبنود وقت التنفيذ.
- `branch_ops_housing_units`, `branch_ops_rooms`, `branch_ops_room_assignments`, `branch_ops_room_inspections`: لا تُنشأ قبل حسم ملكية السكن، السعة، النقل بين الغرف، ومن يتحمل تكلفة/مخالفة.
- `branch_ops_training_programs`, `branch_ops_training_enrollments`, `branch_ops_reward_decisions`: التدريب والنتيجة؛ المكافأة قرار مستقل لا تُرحّل للراتب إلا عبر تكامل رواتب معتمد.
- `branch_ops_cash_custodies`, `branch_ops_cash_handoffs`, `branch_ops_cash_transactions`: لا تُنفذ قبل تحديد الحساب/الصندوق المالي المقابل وقواعد التسوية؛ كل حركة مالية تحمل مرجع قيد حقيقي أو تبقى `pending_posting` بوضوح.
- `branch_ops_integration_connections`, `branch_ops_sync_runs`, `branch_ops_external_metrics`: بيانات تعريف اتصال وحالة مزامنة ومؤشرات Google/التوصيل؛ الأسرار في مخزن الأسرار لا في الجداول.

كل جدول تشغيلي يملك `created_at/created_by/updated_at/updated_by`، وفهارس مركبة تبدأ بـ`branch_id` ثم الحالة/التاريخ حسب الاستعلام. تستخدم المفاتيح الأجنبية للكيانات الحالية. المرفقات تعيد استخدام مسار الرفع والتخزين الحالي؛ يُحسم مرجع المرفق القياسي قبل إضافة علاقة، ولا ينشأ جدول ملفات أو نسخ Blob موازية. الحذف التشغيلي أرشفة، أما أحداث التدقيق والحركات المالية فلا تُحذف.

### دورة الحياة والصلاحيات

- الحالات تنتقل من الخادم فقط وفق مصفوفة انتقالات، مع سبب إلزامي للإلغاء/إعادة الفتح، وتدقيق قبل/بعد.
- `branch_manager`: عرض وإنشاء وتحديث ما يخص فرعه المسموح فقط؛ لا يرى المبيعات أو الرواتب أو المالية لمجرد الدور.
- `operations_manager`: تطبق عليه صلاحيات قالب الدور الفعلية مع مرادفات الوحدات المعتمدة، ويظل النطاق مأخوذاً من الفروع المسموحة فعلياً لا من قيمة `branchId` المرسلة.
- صلاحيات المستخدم الفردية (`view/create/edit/approve/export` لكل وحدة) تبقى نافذة فوق مصفوفة الدور، ويعاد التحقق منها في كل API. صلاحية `sales.view` أو الوحدة الحالية المكافئة مطلوبة لبطاقات المبيعات؛ عند غيابها لا ترسل القيم أصلاً.
- قيود الخادم: الفرع مطلوب، الكميات/المبالغ غير سالبة، التواريخ مرتبة، الموظف/المنتج تابع لسياق مسموح، الانتقال متزامن بقفل/نسخة، ومفتاح idempotency للأفعال القابلة لإعادة المحاولة.

## مراحل التنفيذ

### المرحلة 1 — لوحة الفرع الحالي (منفذة)

**المنفذ في الخادم:** `GET /api/branch-operations/summary?branchId=` يتطلب فرعاً واحداً حقيقياً ومسموحاً، ويطبق صلاحية العرض قبل استعلام مؤشرات كل بطاقة. البطاقات غير المسموحة لا ترسل، وفشل مؤشر بطاقة يعاد كحالة `error` مستقلة لا كقيمة صفر. تعرض المؤشرات الحالية للهدر والمشتريات وطلبات المطبخ والإغلاق والموظفين والوثائق والسلف. عدادات الوثائق تستخدم طبقة القراءة الموحدة نفسها، للموظفين النشطين ومن دون المؤرشف، وروابط تنبيهاتها تحمل الفرع والحالة صراحة. بطاقات الصيانة والأهداف والمبيعات روابط تنقل فقط حالياً؛ لا تدّعي تنبيهات أو أرقاماً غير محسوبة.

**المنفذ في الواجهة:** صفحة RTL متجاوبة للفرع الحالي، ومحدد لا يعرض خيار «كل الفروع»، وتنبيهات قابلة للنقر وروابط عميقة للشاشات الموجودة، وحالات تحميل/خطأ/ممنوع مستقلة. اللوحة للقراءة والتنقل فقط ولا تكتب في المجالات الحالية.

**منع تسرب تبديل الفرع:** يدخل `branchId` و`month` في كل query key، تُلغى طلبات الفرع السابق عند التبديل، لا يستخدم `keepPreviousData` لبيانات حساسة، وتُرفض استجابة متأخرة لا تطابق الاختيار الحالي. الخادم يعيد 403 للفرع غير المسموح حتى لو عُدّل الطلب يدوياً.

**قبول المرحلة:** مدير الفرع يرى فرعه فقط؛ `operations_manager` يرى الفروع التي يسمح بها الخادم؛ الصلاحيات الفردية تحجب البطاقة والبيانات معاً؛ المبيعات مخفية بلا صلاحية صريحة؛ ولا تظهر بيانات الفرع القديم أثناء/بعد التبديل.

### المرحلة 2 — الفجوات التشغيلية اليومية

1. المنتجات غير المتوفرة مع السبب، مدة التوقف، إعادة الإتاحة والتنبيه.
2. صلاحيات دفعات المنتجات والتنبيه، من دون ادعاء حركة مخزون قبل ربطها رسمياً.
3. قوائم فحص إضافية للتنظيف/الجولات فقط بعد مقارنة عدم تكرار قوائم فتح وإغلاق الشفت.
4. **منفذ:** شكاوى الفرع بدورة استقبال وإسناد ومعالجة وحل وإغلاق وإعادة فتح، مع مواعيد استجابة ومرفقات وسجل أحداث.
5. **ما زال غير منفذ:** تطوير بلاغ الصيانة من حالة مخزون إلى بلاغ وإسناد وموعد وإغلاق وتقرير، مع إبقاء سجل الأصل الحالي مرجعاً.

القبول: كل قائمة/بلاغ محدود بالفرع، الانتقالات مدققة، المرفق لا يضاعف التخزين، والتنبيهات قابلة لمنع التكرار.

### المرحلة 3 — مجالات تحتاج قرارات أعمال ومالية

- السكن والغرف والإشغال والتنظيف الدوري.
- تدريب موظفي الفروع والنتائج والمكافآت.
- العهدة النقدية والمصروفات النثرية.
- معنى «تقرير الموظف الشهري للصيانة» ومسؤولية الموظف عن البلاغ.

بوابة البدء: اعتماد مالك المجال، حالات الدورة، حدود المبالغ، المفوضين، سياسة الترحيل، والحسابات المحاسبية. العهدة والنثريات والمكافآت ترتبط بمسار المالية/الرواتب الحقيقي بقيد مرجعي وتسوية؛ **لا** تستخدم ملاحظات يومية الكاشير أو طلب دفع كاختصار محاسبي.

### المرحلة 4 — التكاملات الخارجية

- Google Business Profile: يختار العمل بين API رسمي بحساب مالك وموافقة OAuth، أو إدخال/استيراد يدوي واضح المصدر. تحدد المواقع، حدود المعدل، الاحتفاظ بالنصوص، والردود المسموحة.
- تطبيقات التوصيل: API رسمي لكل مزود أو ملفات تسوية مستوردة؛ تُطابق الطلبات والعمولات والضريبة والتحويلات ولا تستبدل أرقام يومية الكاشير بصمت.

لا مفاتيح في المصدر أو الخطة، ولا تبدأ مزامنة حية قبل اختيار المزود، شروطه، بيئة الاختبار، ومعالجة السجلات المكررة وإعادة المحاولة.

## الاختبار والترحيل والنشر

- اختبارات وحدة لمصفوفة الحالات والصلاحيات والحسابات، واختبارات API لعزل الفروع والدور والصلاحيات الفردية، واختبارات تكامل للتزامن وidempotency، واختبارات واجهة لتبديل الفرع ومنع البيانات القديمة وإخفاء المبيعات.
- اختبارات أداء ببيانات تطوير ممثلة: عدد ثابت من الاستعلامات، صفحات للقوائم، `EXPLAIN` للاستعلامات الثقيلة، وحدود زمن/حجم موثقة.
- كل تغيير قاعدة بيانات ملف SQL **إضافي وصريح**: إنشاء جدول/عمود nullable ثم backfill مراجَع ثم قيد لاحق عند الحاجة، مع فهارس وrollback أو خطة تعافٍ. لا إعادة تفسير للتاريخ ولا حذف تلقائي.
- يمنع `db:push`. تُراجع ملفات migration وتطبق على التطوير/المرحلي أولاً. لا كتابة أو migration في الإنتاج دون موافقة منفصلة ونسخة احتياطية وخطة رجوع.
- النشر تدريجي بعلم ميزة لكل مرحلة/فرع. بعد تطبيق migration المعتمد ثم نشر التطبيق، تنفذ اختبارات smoke بحساب مدير فرع و`operations_manager` وحساب منزوع صلاحية، مع مراقبة 403/5xx وزمن الاستعلام. الرجوع يعطل العلم أولاً ويحافظ على الجداول الإضافية والبيانات.

## قرارات مطلوبة قبل ما بعد المرحلة الأولى

1. ما الفروع والأفعال الإضافية — إن وجدت — التي تعتمد لدور `operations_manager` خارج قالب الصلاحيات الحالي؟
2. هل الزيارات المقصودة ضيوف أم جولات إشراف، وهل الشكوى داخلية أم من عميل؟
3. ما نظام المالية المرجعي للعهدة والنثريات والمكافآت، وما حسابات وترتيب اعتماد كل منها؟
4. هل صلاحية المنتج على مستوى دفعة مخزون فعلية أم مجرد تنبيه تشغيلي؟
