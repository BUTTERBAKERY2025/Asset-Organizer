# Supabase release gap audit — read-only, 2026-09-26

**Decision: NOT release-ready.** This is an object-level inspection of the **documented external target** `irgeqdrdaejhedlcbvzz` using the connected Supabase MCP's read-only SQL. It does **not** establish that Render/current production traffic actually connects to that project. No DDL/DML, migration, `db:push`, deployment, or application runtime test was performed. Confirm Render's effective database target separately, without disclosing its credentials, before treating this as a production certification.

## Evidence and scope

Queried `information_schema.tables/columns`, `pg_constraint`, `pg_indexes`, `pg_trigger`, `pg_proc` in `public`, plus Supabase's migration list. Compared all 359 `pgTable` declarations and 5,559 explicitly named column declarations in `shared/schema.ts` against **369 public base tables / 5,717 columns**. Target metadata includes **1,370 constraints, 1,378 indexes, 16 noninternal triggers and 15 public functions**. Supabase migration history lists 12 recent named entries (from `central_kitchen_reported_available_quantity` through `delivery_notification_outbox`); this is NOT a complete history of all locally numbered scripts and missing history entries are **not** counted as missing objects. Existing 031/033 recipe snapshot/material tables and triggers, the 039 catalogue gates, and many earlier central-kitchen objects are present despite migration-history differences.

The static comparison found **10 absent schema-declared tables** and **99 missing declared columns**: **88 columns belong to those absent tables**, and **11 are missing from existing tables**. **Separately**, `central_kitchen_recipe_exceptions` is an absent raw-SQL table in `043_recipe_exceptions.sql`, not a `pgTable` declaration: **11 runtime-required tables are absent in total** (10 schema-declared + 1 raw SQL). The 99 count **does not include any columns of that raw-SQL exception table**; do not add its columns to the 88/11 breakdown. Twenty public tables are not declared as `pgTable` in the current schema (including the three 033 recipe material/snapshot tables); this is not automatically a fault because raw SQL, older modules and server-side migrations use some of them. There are at least 47 database columns on schema-declared tables not represented by the direct static column-declaration comparison; do not delete them. Column extraction was based on named Drizzle constructors, not full generated SQL; complex indexes/expressions, defaults, implicit serial behavior and cross-schema/Supabase-managed objects require separate review. Metadata inspection cannot certify data quality, runtime target identity, permissions/RLS, application behavior, or rollback readiness.

### Bounded security metadata (not an exploit test)

Read-only `pg_class`/`pg_policies`/`has_table_privilege` inspection covered **12 existing** selected sensitive public tables: `users`, `inventory_items`, `daily_production_batches`, `central_kitchen_order_items`, `central_kitchen_orders`, `central_kitchen_recipes`, `central_kitchen_batch_recipe_snapshots`, `central_kitchen_batch_materials`, `central_kitchen_batch_material_movements`, `production_order_items`, `advanced_production_orders`, `finished_goods_transfers`. Every one has RLS **enabled**, RLS **not forced**, and **zero policies** returned for this set. Effective table privilege checks returned SELECT/INSERT/UPDATE/DELETE = true for the existing `anon`, `authenticated` and `service_role` roles on each. **Grants alone do not prove public data exposure:** for non-bypass roles RLS enabled with no applicable policies ordinarily denies rows, while service/owner bypass behavior and app-level access require separate evaluation. No anonymous API request, login, policy-evaluation probe, or row query was made.

All **eight** selected complaint/maintenance/043/044 tables are absent (`branch_complaints`, `branch_complaint_events`, `branch_complaint_attachments`, `maintenance_tickets`, `maintenance_ticket_events`, `maintenance_ticket_attachments`, `central_kitchen_recipe_exceptions`, `advanced_production_request_links`). The remaining **three** absent tables belong to 042 branch-bar. **Actionable security release blocker:** unlike the separately proposed 045 script, the reviewed local 039 maintenance, 042 branch-bar, 043 exceptions, and 044 links scripts do not explicitly enable RLS or revoke browser-role grants on their new public tables. Before applying them on Supabase, approve and rehearse a least-privilege policy/grants plan for **each** new table/sequence and the intended server DB role; verify its results after application. Do not infer that hypothetical new tables already have unsafe grants or that the existing broad table grants constitute an anon exploit. `FORCE ROW LEVEL SECURITY` may alter privileged server behavior; do not flip it blindly.

Only `storage.buckets` **name and privacy metadata** was read: a single bucket named `documents`, `public = false`. This does **not** verify bucket policies, object access, download/upload rights or private-file behavior. No storage object rows were read.
