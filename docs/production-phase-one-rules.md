# قواعد المرحلة الأولى للإنتاج — مراجعة الشيفرة

**الحالة: اكتملت مراجعة المرحلة الأولى للشيفرة فقط (CODE ONLY)؛ سُجل قرارا المستخدم بتاريخ 2026-09-26 بشأن استثناء وصفة الدفعة المرتبطة بالطلب ومصدر المبيعات المستوردة، وباقي القواعد مسودة اعتماد، لا اعتماد تشغيل شامل ولا إثبات نشر أو مراجعة حية لكل صنف/وحدة/وصفة/عائد/حساب.** هذه قواعد قرار واختبارات قبول، وليست وصفاً لإعدادات البيئة الفعلية. الفهرس: [خط الأساس](production-operating-baseline.md)؛ [سجل التعارضات](production-phase-one-conflicts.md). مالك كل محور أدناه هو **جهة الاعتماد المطلوبة** لا شخصاً ثبتت صلاحياته الفعلية.

## ١. المنتج النهائي مقابل المادة الخام
- **الفرض الحالي:** طلب المطبخ الجديد يلزم `productId` ويمنع `warehouseItemId` ويفرض عدد المنتج الصحيح (`server/central-kitchen-orders.ts:93-129`، `server/routes.ts:8893-8900`). طلب الخام منفصل عبر `/api/warehouse/kitchen-raw-requests` أو نقل المواد (`server/routes.ts:37503-37504`)؛ بنية الوصفة تميز المنتج من مادة المستودع (`shared/schema.ts:13527-13531,13567-13572`).
- **المطلوب:** النهائي → طلب مطبخ، الخام → مستودع/تحويل مستقل؛ لا خلط هوية أو سلة أو حركة واحدة، ولا خصم مستودع عند مجرد طلب النهائي؛ اختيار المطبخ صريح. **غير محسوم:** هوية/وحدات كل صنف حي ومسار التشغيل المنشور. **التحقق الحي:** إصدار الخدمة وطلبات قراءة فقط للكتالوج وأمثلة نهائي/خام مع الفرع والمطبخ، ثم اختبار آمن على بيئة معزولة. **المالك:** مسؤول الإنتاج + المستودع. **القبول:** رفض خام في طلب مطبخ جديد وقبول الخام في مساره بوحدته المعتمدة؛ السجلات الخام التاريخية ظاهرة بلا إعادة تفسير.

## ٢. الوحدات والكسور
- **الفرض الحالي:** طلب النهائي يقبل عدداً صحيحاً للكمية المطلوبة والمتاحة، مع دقة عامة حتى ٦ منازل (`server/central-kitchen-orders.ts:50-59,100-129`)؛ دفعة الخطة صحيحة العدد والوحدة مطابقة للمنتج (`server/advanced-production-execution.ts:16-24,119-126`). طلب خام المطبخ يرفض كسر «قطعة» (`server/routes.ts:37392-37413`). الدفعة اليدوية تختبر `Number(quantity)>0` لكن عمودها integer (`server/routes.ts:23045-23046,23085-23091`، `shared/schema.ts:4250`).
- **المطلوب:** النهائي بعدد صحيح من **وحدة المنتج المعتمدة في الكتالوج** (علبة تبقى علبة، وقطعة تبقى قطعة)، وليس تحويل كل نهائي إلى «قطعة»؛ الخام كسري فقط بوحدة ودقة المادة المعتمدتين، حتى ٦ منازل حيث تدعمها الحركة. الإنتاج النهائي الكسري غير مدعوم الآن؛ يحتاج قراراً لاحقاً بشأن الوحدة والتحويل والتخزين قبل تفعيله، دون افتراض تحويل كوب/علبة/كيلو إلى قطعة. **غير محسوم:** الوحدات الفعلية لكل صنف وتوحيد حد اليدوي. **التحقق الحي:** قراءة catalog/mapping ووحدات الطلب والدفعة بلا تخمين؛ لم يحدث فحص حي لكل وحدة. **المالك:** الإنتاج + المستودع. **القبول:** رفض نصف وحدة نهائية معتمدة، وقبول العدد الصحيح من «علبة» إن كانت هي الوحدة المعتمدة؛ قبول نصف كيلو خام معتمد فقط، ورفض دقة/وحدة غير معتمدة؛ التقارير تفصل الوحدات.

## ٣. عهدة المطبخ والمستودع والبار والأرصدة
- **الفرض الحالي:** تجهيز طلب المطبخ الحقيقي يحجز عبر `reserveRealPreparation`، والإرسال يصرف الحجز ويحرر غير المرسل، واستلام الوجهة يضيف المستلم عبر `receiveRealInventory` (`server/routes.ts:9239-9242,9377-9388`، `server/central-kitchen-live.ts:463-480,530-547,559-624,629-687`). نقل النهائي مطبخ→مستودع مُدار يحجز من دفعة المنتج عند الطلب، يخصم المصدر عند الإرسال، ويضيف المستلم إلى رصيد المستودع المُدار عند الاستلام (`server/kitchen-warehouse-shipping-routes.ts:103-120,169-203`). عهدة مطبخ الفرع→البار تخصم المنتج من مصدر الفرع عند الإرسال، وتضيف السليم إلى `branchBarStock` والتالف إلى حجر منفصل عند الاستلام، لا إنتاجاً جديداً (`server/branch-bar-handoffs.ts:129-161,168-180`). الخام يسلك تحويل المستودع المستقل (`server/routes.ts:37503-37506,37794-37840`).
- **المطلوب:** دفتر عهدة منفصل لكل موقع/هوية/وحدة: حجز ≠ صرف ≠ استلام، ولا خصم من المستودع الرئيسي بسبب طلب نهائي، ولا إضافة إنتاج ثانية عند تسليم البار، ولا عدّ التالف رصيداً صالحاً؛ فروق الاستلام المفتوحة لا تُسوى ضمنياً. **غير محسوم:** أرصدة الافتتاح لكل موقع، الترحيلات ووضع real/shadow ومطابقة التحويل الخام الحي؛ استلام البار لا يثبت رصيده بعد المبيعات. **التحقق الحي:** جرد افتتاحي معتمد للمطبخ/المستودع/بار الفرع ولكل صنف ووحدة، وقراءة قيود قبل/بعد لدورة معزولة مع فرق/تكرار. **المالك:** قادة المطبخ والمستودع والفرع + مالك المخزون. **القبول:** كل حركة للمصدر/الوجهة مرة واحدة فقط، السليم وحده متاح، التالف/الناقص منفصل، ومطابقة الأرصدة الموقعة قبل تمكين real.

## ٤. الوصفات والعوائد وناتج الدفعة
- **الفرض الحالي:** تنفيذ بند خطة معتمدة/جارية فقط، يتحقق من نهائي نشط ووحدة مطابقة؛ ينشئ دفعة `in_progress` بلقطة وصفة إلزامية، والإتمام وحده ينشر المخزون (`server/advanced-production-execution.ts:45-48,95-148,153-175`). حساب المادة `مكون × ناتج الدفعة ÷ ناتج الوصفة` يرفض باقي الدقة بدل التقريب (`shared/central-kitchen-batch-materials.ts:31-57`)؛ الوصفة ذات ناتج موجب ومواد موجبة (`shared/schema.ts:13527-13578`). إنشاء الخطة المباشر/AI يتحقق من مرجع قابل للاختيار، لا يثبت في الموضع نفسه نوع النهائي وكمية هدف صحيحة (`server/routes.ts:18758-18794,21576-21628`).
- **المطلوب:** الخطة مستهدف لا مخزون؛ تنفيذ الخطة بوصفة معتمدة ولقطة ثابتة للهويات والوحدات والعائد، لا إعادة احتساب الماضي؛ رفض ناتج لا يمكن صرف مكوناته بدقة. **قرار المستخدم 2026-09-26 للدفعة الجديدة المرتبطة بطلب فقط:** المسار القياسي مدعوم بوصفة، ويجوز استثناء بلا وصفة **فقط بموافقة مسؤول الإنتاج**؛ ليس `recipeBacked=false` المفتوح حالياً (`server/central-kitchen-orders.ts:258-265`، `server/routes.ts:8679-8703`) تطبيقاً لهذا القرار. التنفيذ المتقدم يظل صارماً حتى تنفيذ سياسة مقصودة ومراجعتها؛ لا يُعمم عليه الاستثناء. **متطلبات تنفيذ لم تُبنَ بعد:** توثيق نطاق الاستثناء وهوية الدفعة/الطلب وسببه والموافق ووقت الموافقة في أثر قابل للتدقيق، ورفض إنشاء دفعة جديدة بلا وصفة إذا غابت الموافقة المعتمدة؛ هذه ليست سياسة رفض إضافية اعتباطية ولا وصفاً لحارس قائم. **غير محسوم:** الوصفات المعتمدة والعوائد الفعلية لكل صنف، وصحة كل هدف خطة؛ لم تُراجع حياً. **التحقق الحي:** قراءة نسخ الوصفات والعوائد وربط البنود واللقطات وحالات الدفعات والترحيلات. **المالك:** مدير الإنتاج + مسؤول الوصفات. **القبول:** التنفيذ المتقدم لا يبدأ بلا لقطة وصفة/عائد؛ مسار الطلب المرتبط يقبل الاستثناء المعتمد فقط ويرفض غيابه، مع بقاء مسار الوصفة القياسي؛ الإلغاء قبل الإتمام لا يرحّل، والإتمام مرة واحدة؛ البنود غير الصالحة تُعزل قبل التنفيذ.

## ٥. الأدوار والصلاحيات
- **الفرض الحالي:** حالات طلب المطبخ مستقلة؛ create وapprove بصلاحيتين مختلفتين، وprepare/dispatch/receive تشترك في edit (`server/routes.ts:8893-8897,9503-9514`). نقل الخام: create وedit مع تحقق نطاق المصدر للاعتماد/الإرسال والوجهة للاستلام (`server/routes.ts:37503-37506,37531-37563,37794-37840`). عهدة البار تمنع المنشئ والمرسل من تأكيد الاستلام (`server/branch-bar-handoffs.ts:90-115`). هذه **حراس مسارات لا منح حسابات فعلية**.
- **المطلوب:** طلب → اعتماد → تجهيز → إرسال → استلام بحسب المسار؛ الاستلام من الوجهة المخولة، لا السائق أو المرسل تلقائياً؛ فصل أثر الحجز والصرف والإضافة والفروق، وإعادة المحاولة دون ازدواج. الشحن المباشر مطبخ→مستودع وعهدة البار لهما دورات مختلفة حالياً، لا نفترض لهما اعتماداً غير موجود (`server/kitchen-warehouse-shipping-routes.ts:123-149`، `server/branch-bar-handoffs.ts:90-115`). **غير محسوم:** مصفوفة تفويض الحسابات الفعلية وما إذا لزم فصل صلاحيات إضافي. **التحقق الحي:** حسابات اختبار معتمدة لكل دور وفرع، رفض/سماح لكل فعل، وجرد قبل/بعد. **المالك:** مالك الصلاحيات + قادة المصدر والوجهة. **القبول:** كل انتقال مقيد بالحالة والنطاق والفاعل المعتمد؛ لا استلام من جهة المصدر دون تفويض وجهة، مع أثر فرق مستقل.

## ٦. مصدر مبيعات كل فرع
- **الفرض الحالي:** يوجد جدول POS به branch/date ومفتاح عدم تكرار (`shared/schema.ts:11440-11483`) وتقارير تجمع اليوميات النقدية (`server/routes.ts:386-406`)؛ ليست اليومية إثبات كمية منصرفة. سياسة الفصل قائمة (`docs/production-operating-baseline.md:15-16,30`).
- **المطلوب:** **قرار المستخدم 2026-09-26:** مصدر المبيعات هو الاستيراد من نظام خارجي؛ ليس ذلك اليومية النقدية للكاشير ولا إثباتاً بأن كل التقارير المالية تحولت إلى هذا المصدر. يلزم ربط الاستيراد بالصنف والوحدة والفرع والفترة ومفتاح يمنع تكرار الاستيراد أو الخصم مرتين، وفصل أثر المرتجع والهدر؛ لا يساوي مجموع استلام البار رصيده بعد البيع. لا يُحذف POS ولا يُعطّل بناءً على هذا القرار. **غير محسوم:** قائمة الفروع الحية وخرائط المصدر والفترات الفعلية لكل فرع، هوية الصنف/الوحدة المستوردة، معالجة الاستيراد المكرر والمرتجعات، ledger البار والأرصدة الافتتاحية؛ لم تُراجع حسابات أو mapping حية. **التحقق الحي:** قائمة الفروع الفعلية وإعدادات استيراد المصدر وفتراتها ثم مجاميع قراءة فقط matched/unmatched/void/refund وحركات بار opening/receipt/sale/waste/closing بلا بيانات شخصية. **المالك:** مالك المبيعات/المالية + مدير كل فرع + المخزون. **القبول:** لا رصيد بار «حي» قبل إثبات الربط والخصم/العكس مرة واحدة؛ المجهول منفصل ولا تخمين مطابقة.

## ٧. التعطيل والسجلات القديمة
- **الفرض الحالي:** اختيار المرجع التشغيلي يسمح `isActive` غير معطل **أو** `operationsEnabled=true`؛ بوابة البيع أشد (`shared/catalog-activity.ts:6-42`). طلب المطبخ يستخدم OR مماثلاً (`server/routes.ts:7777-7783,7824-7873`)، لكن منفذ دفعة الخطة يفحص `isActive` فقط (`server/advanced-production-execution.ts:119-122`). إنشاء منتج غير مسعّر قد يسجله `isActive=false,operationsEnabled=true` (`server/routes.ts:7314-7321`).
- **المطلوب:** التفريق صراحة بين «مسموح تشغيلياً وغير معروض للبيع» و«معطل تشغيلياً»؛ لا ترفض منتجاً صالحاً للتشغيل بسبب عدم عرضه للبيع، ولا تستخدم معطلاً تشغيلياً في إنشاء جديد؛ حافظ على ظهوره في التاريخ، ولا تحجب بقية احتياج مختلط. **غير محسوم:** دلالة الحقلين في الكتالوج الحي وتوافق منفذ الخطة مع سياسة العمليات. **التحقق الحي:** قراءة عينات كل تركيب للحقلين ومسارات الاختيار/التنفيذ؛ ليس حكم تعطيل شامل من `isActive` وحده. **المالك:** مالك الكتالوج + الإنتاج. **القبول:** مصفوفة نشاط معتمدة مختبرة على كل مدخل، وتاريخ معطل قابل للقراءة.

- **الفرض الحالي:** اليدوي المستقل يتطلب إقراراً ومفتاح عدم تكرار ويرفض حقول الربط/الوصفة ويكتب `recipeBacked=false` (`server/routes.ts:23002-23032,23101-23104`)؛ **هذا مسار مقصود، ليس استثناء الدفعة المرتبطة ولا ثغرة بذاته**. دفعة طلب المطبخ المرتبطة تسمح `recipeBacked=false` افتراضياً، ولا تلتقط وصفة إلا إن كان true (`server/central-kitchen-orders.ts:258-265`، `server/routes.ts:8679-8703`): **فجوة تنفيذ سياسة القرار المحسوم** بشأن الجدد، لا دليل استغلال ولا إثبات موافقة. القديم NULL للوصفة (`shared/schema.ts:4263-4265`)؛ وضع طلب جديد يثبت real/shadow عند الإنشاء (`server/routes.ts:8960-8965`).
- **المطلوب:** لا حذف/إسناد رجعي/إعادة حساب للقديم؛ اليدوي لا يُنسب إلى طلب أو صرف وصفة؛ فصل real/shadow/unknown. الدفعة الجديدة المرتبطة بطلب بلا وصفة استثناء بموافقة مسؤول الإنتاج فقط، بهوية ونطاق وسبب وموافق ووقت قابلين للتدقيق عند التنفيذ؛ غياب الموافقة يوجب رفض الاستثناء بعد تنفيذ الحارس، دون تحويل اليدوي إلى بديل صامت. **غير محسوم:** سجل التشغيل الفعلي والهجرة المنشورة. **التحقق الحي:** قراءة modes والدفعات التاريخية وروابطها دون mutation. **المالك:** الإنتاج + مالك الترحيل. **القبول:** غير المعروف يبقى غير معروف، ولا قيد مزدوج أو حذف؛ اختبار المسارين القياسي والاستثنائي والرجوع قبل أي تغيير.

**منع الإطلاق التشغيلي:** لا تحويل إلى real أو تعميم قبل إثبات artifact/migrations والإعدادات الحية والأرصدة الافتتاحية، استكمال سياسة الكتالوج والوصفة والكسور، اختبار صلاحيات المستلم وربط المبيعات المستوردة لكل فرع، ودورة محدودة بمالك ونسخة احتياطية وخطة رجوع؛ انظر سجل التعارضات. **القراران حُسما في 2026-09-26، لا التنفيذ أو التحقق:** (١) استثناء الدفعة الجديدة المرتبطة بطلب بلا وصفة يحتاج موافقة مسؤول الإنتاج الموثقة وحارس رفض عند غيابها. (٢) المبيعات مستوردة من نظام خارجي، وتبقى قائمة الفروع الفعلية وخرائط المصدر/الهوية/الوحدة والفترات والمرتجعات والتكرار بحاجة إلى إثبات. لا تُخترع فروع أو خرائط، ولا يُحذف POS أو يُعطّل، ولا يُدّعى تحويل كل التقارير المالية؛ النهائي حالياً عدد صحيح من وحدته المعتمدة، ولا يُفعل كسره بلا قرار لاحق.
