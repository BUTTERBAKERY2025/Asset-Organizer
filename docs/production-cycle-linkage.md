# ترابط دورة إنتاج المطبخ المركزي

## حدود هذه المراجعة

هذه وثيقة تحقق للنسخة الموجودة في المشروع، وليست إثباتاً أن المهام المنفصلة
دُمجت أو أن التغييرات نُشرت على Render. اختبارات قاعدة التطوير لا تثبت تنفيذ
حركة فعلية في قاعدة التشغيل. لا تُنشأ حركات تجريبية في المخزون الحقيقي.

## تسلسل العمل ومصدر الحقيقة

| المرحلة | يعتمد على | النتيجة المطلوبة |
|---|---|---|
| اعتماد كتالوج الأصناف | كود تجاري معتمد، رقم داخلي ثابت، نوع الصنف ووحدته | تحديث الهوية التجارية دون قطع روابط السجلات |
| إعداد الوصفة واعتمادها | منتج نهائي، ناتج محدد، مواد ووحدات وكميات صحيحة | إصدار معتمد؛ الاعتماد وحده لا يصرف مخزوناً |
| طلب الفرع | هوية منتج أو مادة، فرع طالب ومطبخ، كميات صحيحة | طلب جديد يحفظ هوية بنوده ووحداتها ووضع المخزون |
| اعتماد الطلب | صلاحية ونطاق فرع مناسبين | السماح بالتخطيط والتجهيز، وليس حركة صرف بحد ذاته |
| تحديد الاحتياج | المخزون الحر والحجوزات والدفعات المرتبطة | عدم احتساب المخزون نفسه متاحاً بالكامل لكل طلب |
| إنشاء الدفعة المرتبطة | بند معتمد واحتياج غير مغطى ووصفة صالحة عند اختيار إنتاج بالوصفة | ربط الدفعة بالبند وتجميد نسخة الوصفة والمواد |
| إتمام الدفعة | مواد كافية في المطبخ، حالة قابلة للإتمام | صرف المواد وإضافة الناتج مرة واحدة داخل معاملة |
| تجهيز الطلب | ناتج موثق أو مخزون جاهز أو مزيج منهما | حجز إجمالي التجهيز مرة واحدة؛ المصادر ليست أرصدة مستقلة |
| إرسال الطلب | تجهيز وحجز صالحان | خصم المرسل من مخزون المطبخ وتسجيل الحركة مرة واحدة |
| استلام الفرع | إرسال قائم وكميات سليمة/تالفة/ناقصة محددة | إضافة السليم فقط لمخزون الفرع وتسجيل الفرق |
| معالجة الفرق | طلب مستلم وفرق مفتوح وصلاحية مناسبة | حفظ قرار المعالجة وأثره التدقيقي دون محو الفرق الأصلي |
| التقارير | دفعات وحركات وطلبات مرتبطة وحالات فرق صريحة | عدم مضاعفة الناتج أو جمع وحدات مختلفة أو اعتبار الفرق المحسوم مفتوحاً |

## قواعد لا يجوز أن يغيّرها اعتماد الأكواد

- كود الملف هو `sku`، وليس `id`. لا تعاد تسمية الأرقام الداخلية أو إنشاؤها
  من الأرقام الموجودة في Excel.
- هوية المنتج منفصلة عن هوية مادة المستودع؛ تساوي رقمين لا يجعلهما الصنف نفسه.
- تغيير الاسم والكود ليس تحويل وحدة، ولا نقل رصيد، ولا تغيير سعر.
- الاسم العربي الحالي والاسم الثنائي اللغة قد يعودان إلى الصنف نفسه.
  عدم تطابق الكود لا يكفي لإضافة صنف جديد أو حذف القديم.
- تحفظ الأقسام المتعددة كاستخدامات للصنف الواحد، لا كنسخ مكررة منه.
- لا تُعدّل نسخة وصفة مجمدة أو اسم محفوظ في حركة تاريخية لمجرد تعديل الكتالوج.
- لا يعطل صنف مطلوب لوصفة أو طلب مفتوح دون إظهار الأثر ومعالجته.
- لا يعتبر غياب المراجع المقيدة بمفاتيح خارجية دليلاً كافياً لأمان الحذف:
  يلزم أيضاً فحص الرصيد، والحجوزات، والحركات المفتوحة، والمراجع غير المقيدة.
- لا تُستنتج روابط للطلبات أو الدفعات القديمة من الأسماء. السجلات القديمة
  ذات وضع المخزون أو ارتباط الوصفة غير المحدد تبقى مميزة عن التشغيل الفعلي.

اختبارات Node أو استدعاء معالجات الخادم لا تعادل اختبار المتصفح داخل حساب.
اختبار المعاملة الواحدة لا يثبت كل حالات السباق بين اتصالات مستقلة.
تُراجع النتائج الفعلية لكل تشغيل، ولا يُفترض نجاح اختبار لم يُشغّل.

## بوابات التحقق قبل الاعتماد النهائي

1. دمج التغييرات المنفصلة ذات الصلة أولاً، ثم فحص الشيفرة الفعلية؛ حالة
   «منفذة» للمهمة لا تعني أن شيفرتها موجودة في النسخة الرئيسية.
2. مراجعة خريطة ربط الأصناف الحالية بالأكواد الجديدة قبل تنفيذها، مع
   حفظ الأسعار والأرصدة وعدم حذف سجلات مرتبطة.
3. إثبات قبول كسور المواد ورفض كسور المنتجات النهائية في مسار إنشاء الطلب،
   وليس في نموذج البيانات أو دوال المخزون فقط.
4. إثبات وجود معالجة آمنة لدفعة متعطلة وتكرار المحاولة، دون مضاعفة المخزون.
5. اختبار سحب صلاحية الوصفة ونطاق المطبخ بعد تحميل البيانات في الذاكرة المؤقتة.
6. التحقق من أثر تغيير الأكواد على دورة قائمة، ثم تشغيل اختبارات التكامل
   في قاعدة التطوير بمعاملات تُلغى في النهاية أو مخطط اختبارات معزول.
7. قبل أي تطبيق على قاعدة التشغيل: تحديد الهدف، توفير مسار استرجاع،
   إعادة فحص أحدث المراجع والأرصدة، واعتماد الإجراءات المقترحة.
8. لا تُفسّر معالجة فرق إدارياً بأنها قيد مالي أو حركة مخزون تعويضية
   ما لم توجد حركة صريحة موثقة تثبت ذلك.
